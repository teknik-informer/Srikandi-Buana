Date: 2026-11-24

## Decision

Use the V9.2.0 transfer package as the UI/UX reference and public-site/application shell. Retain the V9.1 operational core as the only source of truth for identity, authorization, and persistent operational data. This is a separate integration branch, but not an independent Git lineage. At integration commit `3ebf45a1a054d7c201f329129e1fe504994ae10d`, GitHub comparison identifies `2f8797a0f5bc78603c5f5be01384cf3770e0c13b` (the `feat/v9-operational-core` tip) as the merge base, with this integration branch 25 commits ahead. The V9.2.0 design commit `ac5c24041dced147ab2589174c8e9df8e809f767` is also an ancestor. Keep the branches as separate refs; do not describe this branch as isolated from the operational-core lineage, and do not merge or rebase source branches casually.

- Do not use demo credentials or copy demo account identities into the real database.

## Non-negotiable integration rules

1. Do not merge V9.2.0 demo authentication, demo session cookies, or localStorage persistence into production.
2. Do not replace or reset the existing V9 development database or its 19 recorded migrations.
3. Preserve V9.1 native finance journal integrity and approval/reversal rules.
4. Route every operational read/write through server-side services with organization scoping, authorization, validation, and audit events.
5. Keep website CMS settings separate from operational domain data; do not treat browser-local settings as authoritative production content.
6. Keep this integration branch as a Preview candidate. No Production deployment or domain change until user acceptance.

## Integration sequence

1. Inventory V9.2 routes, components, domain entities, forms, and actions against the V9.1 server services and schema.
2. Port the V9.2 visual shell and public pages into the separate integration branch without replacing V9.1 server identity/session modules.
3. Replace localStorage-backed operational reads and writes with typed server actions/services, starting with membership and Secretariat, then field applications, native finance, inventory/orders/POS, and portals.
4. Replace the demo login form with the V9.1 server authentication contract; provision the first administrator only after Preview environment variables are configured and verified.
5. Add migration-safe tests, role-based tests, and responsive regression checks.
6. Build and deploy a separate Preview. Keep existing production and legacy deployments untouched.

### Availability risk and remediation

The three pages above, plus product detail, query Neon during server rendering. If the database connection is unavailable, the current server-render path can throw and cause an HTTP 500. The missing database URL in Arena's local environment explains its local 500 result; the actual Preview deployment did not reproduce that failure while its Preview database configuration was available.

A public-segment `error.tsx` should provide a friendly retry state and prevent a blank error experience, but it is only an error boundary. It does not replace backend resilience. The backend owner will separately implement explicit unavailable-data handling (distinct from a genuine empty result) and evaluate a bounded cache/stale-data strategy for public read-only views. Do not expose internal database errors, secrets, or stack traces to visitors.

### Central organization approval inbox — domain-backed queues, 24 November 2026

The old generic approval page that read `APPROVALS` from the browser demo store has been replaced with three organization-scoped queues backed by their own domain tables:

1. **Finance journals** — reads `v9.finance_journals` with status `submitted`. Approve/reject actions call the native finance review action, which enforces `finance:journal:approve`, prevents self-approval, requires a rejection note, and records approval/rejection plus audit data. Approval changes the journal to `approved`; it does not post it to the ledger. Posting remains a separate controlled action.
2. **Membership interests** — reads `v9.membership_interests` with status `submitted` or `under_review` only for users with `field:organisasi:review`. The existing decision action continues to match/create a person, prepare a membership in pending-verification status after approval, record reviewer metadata, and write an audit event. The inbox can start review, accept, or reject.
3. **Field workplans** — reads `v9.field_workplans` with status `submitted`. Approval requires `organization:team:approve`, updates `approved_by`/`approved_at`, and writes an audit event in the same SQL statement. The schema has no rejected/revision status for this entity, so the inbox does not offer a misleading "reject" action.

Security and usability:
- Every query is scoped to the authenticated `organization_id`.
- Finance creator cannot approve their own submitted journal; the action also rejects self-approval at the database update predicate, not only in the UI.
- Membership applicant phone/address are queried only for users with the organization-review permission; users without that permission see an access-restricted notice rather than a false zero count.
- Source read failures are surfaced per queue; incomplete data is not presented as a complete zero total.
- Links lead back to the source finance journal and field workplan modules for detailed inspection.
- The approval page and client no longer import `useStore()`, `APPROVALS`, or browser `localStorage`.

### Secretariat dashboard migration — 24 November 2026

The Secretariat workspace landing route `/app/sekretariat` has been migrated from the V9.2 demo `useStore()`/seed-data dashboard to organization-scoped Neon reads.

Implementation:
- The server page now requires `secretariat:read` and reads summary counts from `v9.secretariat_letters`, `v9.secretariat_documents`, and `v9.secretariat_meetings`.
- The latest incoming letters are sourced from the letter register. Authorized Secretariat users can advance a letter from `baru` to `diproses` and then `selesai` through the existing server action.
- Upcoming meetings are sourced from the meeting register and include the latest minutes revision status and actual attendance count.
- Recent documents show their real register reference, category, visibility, and status.

- Letter status updates now revalidate `/app/sekretariat` as well as the letter and expedition routes.
- A data-source failure produces a sanitized warning and an explicit unavailable message; a successful zero-row query produces genuine empty states instead of fabricated demo counts.

### Finance receipts and payments views migrated to native journal data — 24 November 2026

The read-only pages `/app/keuangan/penerimaan` and `/app/keuangan/pembayaran` no longer import static `JOURNALS` or hardcoded chart-of-account labels.

Implementation:
- Both pages require `finance:read` and read organization-scoped rows from `v9.finance_journals`, `v9.finance_journal_lines`, and `v9.finance_accounts`.
- Receipt movements are derived from debit lines on cash/bank accounts `1-1000` and `1-1100`; payment movements are derived from credit lines on those accounts.
- Counterpart account labels are read from the journal's actual opposite-side lines, not a client-side static map.
- Posted totals only include journals with status `posted`; draft, submitted, approved and rejected items remain identifiable by their real workflow status and do not inflate posted totals.
- The pages are deliberately read-only. They do not pretend that a dedicated receipt/payment intake form, payment evidence workflow, or member-specific contribution attribution has been completed.
- Database failures show a clear unavailable state, with sanitized server logging; a valid empty result is shown separately.

- Read-only QA checks found 0 journals with cash/bank debit movements and 0 journals with cash/bank credit movements for the QA organization. No transaction or journal fixture was inserted.
