# V9.2.0 Production Integration Audit

Date: 2026-11-24

## Decision

Use the V9.2.0 transfer package as the UI/UX reference and public-site/application shell. Retain the V9.1 operational core as the only source of truth for identity, authorization, and persistent operational data. This is a separate integration branch, but not an independent Git lineage. At integration commit `3ebf45a1a054d7c201f329129e1fe504994ae10d`, GitHub comparison identifies `2f8797a0f5bc78603c5f5be01384cf3770e0c13b` (the `feat/v9-operational-core` tip) as the merge base, with this integration branch 25 commits ahead. The V9.2.0 design commit `ac5c24041dced147ab2589174c8e9df8e809f767` is also an ancestor. Keep the branches as separate refs; do not describe this branch as isolated from the operational-core lineage, and do not merge or rebase source branches casually.

## Verified V9.1 operational-core facts

- The isolated schema is `v9` and the database connection is intentionally read from `V9_DATABASE_URL`.
- Login uses Neon SQL, scrypt password verification, HMAC-based rate-limit identifiers, opaque random session tokens, and server-side role assignments.
- The first organization administrator is created by the one-time `scripts/bootstrap-v9-admin.mjs` script.
- Bootstrap requires `V9_DATABASE_URL`, `V9_BOOTSTRAP_NAME`, `V9_BOOTSTRAP_EMAIL`, `V9_BOOTSTRAP_PASSWORD`, and the explicit confirmation value `CREATE_FIRST_ORGANIZATION_ADMIN`.
- Do not use demo credentials or copy demo account identities into the real database.

## Non-negotiable integration rules

1. Do not merge V9.2.0 demo authentication, demo session cookies, or localStorage persistence into production.
2. Do not replace or reset the existing V9 development database or its 19 recorded migrations.
3. Preserve V9.1 native finance journal integrity and approval/reversal rules.
4. Route every operational read/write through server-side services with organization scoping, authorization, validation, and audit events.
5. Keep website CMS settings separate from operational domain data; do not treat browser-local settings as authoritative production content.
6. Keep this integration branch as a Preview candidate. No Production deployment or domain change until user acceptance.

## Integration sequence

1. Inventory V9.2 routes, components, domain entities, forms, and actions against the V9.1 server services and schema.
2. Port the V9.2 visual shell and public pages into the separate integration branch without replacing V9.1 server identity/session modules.
3. Replace localStorage-backed operational reads and writes with typed server actions/services, starting with membership and Secretariat, then field applications, native finance, inventory/orders/POS, and portals.
4. Replace the demo login form with the V9.1 server authentication contract; provision the first administrator only after Preview environment variables are configured and verified.
5. Add migration-safe tests, role-based tests, and responsive regression checks.
6. Build and deploy a separate Preview. Keep existing production and legacy deployments untouched.

### Availability risk and remediation

The three pages above, plus product detail, query Neon during server rendering. If the database connection is unavailable, the current server-render path can throw and cause an HTTP 500. The missing database URL in Arena's local environment explains its local 500 result; the actual Preview deployment did not reproduce that failure while its Preview database configuration was available.

A public-segment `error.tsx` should provide a friendly retry state and prevent a blank error experience, but it is only an error boundary. It does not replace backend resilience. The backend owner will separately implement explicit unavailable-data handling (distinct from a genuine empty result) and evaluate a bounded cache/stale-data strategy for public read-only views. Do not expose internal database errors, secrets, or stack traces to visitors.

### Build-count terminology

The Vercel build log for commit `75a31ed` reports Next.js static generation progress `145/145`. Arena's local report identifies 15 prerendered manifest routes and 51 entries beneath `.next/server/app`. These are different artifacts and measures; the number 145 must not be described as 145 unique public routes or 145 user-facing pages. Report route counts from the route manifest, and framework generation progress separately.

### Operational persistence audit — open release blocker

The V9 schema and server-action foundation exist, but the UI is not yet fully migrated from the V9.2 demo store to shared Neon persistence. The code review confirmed:

- `src/lib/store.tsx` still describes and implements browser-local `localStorage` persistence for demo operational state.
- `src/components/core-shell.tsx` mounts that `StoreProvider` for the workspaces.
- The Pengurus dashboard, approval workspace, Anggota dashboard, and POS terminal still consume `useStore()`; their demo-store mutations are therefore browser-local rather than authoritative organization records.
- Some operational paths are already server-backed, including membership status management, Secretariat letters/documents, the native finance journal workflow, and agriculture/training/business actions. This does not mean every screen or action in those domains has been migrated.
- The finance dashboard itself documents that cash/bank reconciliation, budgets, dues, receivables/payables, POS integration, and business-transaction posting remain unconnected.

Do not remove or silently repurpose the demo store until each dependent screen has a replacement server query/mutation, authorization check, audit trail, loading/empty/error states, and a verified migration path. Keep demo data clearly marked as demo until this work and authenticated acceptance are complete.

### Field-action authorization hardening — 24 November 2026
