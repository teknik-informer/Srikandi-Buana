## Confirmed operational findings

### 1. File storage configuration exists; metadata persistence is failing

The three required variables (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET`) are now present in Vercel and targeted to both Production and Preview. Their secret values were not retrieved or exposed. The operator confirms that uploaded files appear in Cloudinary, so this is no longer primarily an environment-variable setup problem.

The Cloudinary account usage snapshot previously reported 65 resources and approximately 180.1 MB in use. Production runtime logs recorded two `/api/files` failures with `NeonDbError` after the upload routine, at approximately 11:50 and 11:57 WIB on 28 November 2026. This matches the operator's observation that Cloudinary receives the file while the application reports failure during database persistence.

**Previously released change:** an authenticated GET preflight on `/api/files` checks Cloudinary configuration readiness without returning credentials. **Current fix branch:** gives `scope` and `category` explicit `text` types inside the JSONB audit constructor, separates Cloudinary upload from database persistence for diagnostic logging, and returns a safe message that tells the operator not to upload the same file again when Cloudinary has already accepted it but Neon has failed.

**Configuration action completed:** the three variables were targeted to Production and Preview on 28 November 2026. **Remaining validation:** after the typed-parameter fix is deployed, perform one authenticated test upload, confirm a matching `v9.file_assets` row and `file.uploaded` audit event, then test listing, preview/download, and share-link permissions. Do not delete existing Cloudinary assets until orphan ownership is reconciled.

### 2. Database access hardening

The production `v9` schema contains 63 application tables. At validation time, row-level security is enabled on 0 of 63. The `v9_app` role has application CRUD grants across this schema. Current isolation and authorization therefore depend on server-side identity resolution, permission checks, and organization-scoped SQL.

Do not enable RLS with a blanket migration. The application uses the Neon serverless HTTP query client, and its current shared query helper does not establish a per-request organization context or transaction-local security context. Enabling policies before refactoring that request context would cause legitimate reads/writes to fail or, worse, create policies that do not enforce the intended tenant boundary.

**Required implementation sequence:**
1. Inventory all reads/writes and their organization, unit, self, and public scope.
2. Add a request-bound database context mechanism that is transaction-safe with Neon HTTP pooling and cannot leak between requests.
3. Define policy tests for each role and scope, including anonymous/public access and cross-organization negative cases.
4. Enable RLS in a staged migration on a Preview database, run regression/UAT, then deploy only after measured verification.
5. Reassess broad DELETE grants separately; do not revoke them until the action inventory identifies every dependency.

No RLS or privilege changes were made in this branch.

### 3A. Source-to-target reconciliation evidence

A second read-only pass inspected payload **field names and aggregate status values only**; personal names, phone numbers, addresses, and raw payload values were not returned.

- All nine `public.records` payloads are JSON objects. The five `anggota` objects use the fields `name`, `phone`, `dusun`, `potential`, `role`, `status`, `verification`, and `consent`. All five show the legacy labels `Aktif`, `Terverifikasi`, and `Terdokumentasi` in aggregate.
- All five member records have an `owner` link to a legacy user; four also have an explicit `member_id` link. All five V9 `people` rows already link to a legacy user through `legacy_source_user_id`. This strongly indicates that V9 people rows should be reused during reconciliation; a migration must not create five duplicate people.
- The one `workspace_v14.member_profiles` row links to a legacy member record and, through that record's owner, to a person already present in V9. Its status is `pending_verification`, identity verification is pending, and data consent is `not_requested`. Its structured `operationalProfile` contains the keys education, experience, interests, skills, languages, certifications, and volunteer.
- Both `workspace_v14.organization_memberships` rows link to legacy users and are active (admin and chair). Each already matches an existing V9 role assignment when reconciled through legacy user → V9 person → V9 account: admin 1/1 and chair 1/1. No new role assignment is needed for these two rows; retain the V9 assignments as authoritative and do not duplicate or elevate permissions from legacy role fields.
- The V9 `memberships` table currently has zero rows. The legacy `anggota` status/verification/consent labels alone do not supply a structured consent version, consent timestamp, or evidence reference. The separate V14 profile explicitly says consent was not requested. Therefore, the import must preserve these as reviewable source facts and must not silently mark the V14 profile as consented or convert its pending verification into an active membership.
- Legacy `program` contains only name, notes, programId, and status; it lacks the V9 `field_key` and other operational planning dimensions. The single legacy `surat_resmi` is marked `Draf`; its letter fields require explicit mapping to V9 secretariat-letter semantics. `kelembagaan` and `register` also need a defined archive/metadata destination. These rows should be retained and staged for manual reconciliation, not forced into the nearest V9 table.
- The old `public` setting contains 23 named content fields for public identity, contact, hero, logo, mission, vision, and social links. At the latest database inspection, V9 already contains `public_site`, `public_profile_content`, and `login_page_content` settings. The legacy `heroFileId` and `logoFileId` references still need separate asset reconciliation; do not assume old media IDs are valid V9 file-asset IDs.

**Recommended migration shape:** reuse the established V9 person/account links; import only rows whose ownership and mapping are deterministic; stage consent, identity verification, membership activation, letter publication, and external-sharing decisions for explicit review; preserve every legacy source ID and produce a before/after reconciliation count. The first implementation should be a dry-run report with zero writes.


## 6. Deep functional and governance audit — 28 November 2026, 12:07 WIB

### 6.1 Two confirmed persistence failures

**Pusat Berkas**

- The production log shows two failed `POST /api/files` requests with `NeonDbError`, approximately 11:50:05 and 11:57:21 WIB.
- The application flow uploads the bytes to Cloudinary first, then inserts `v9.file_assets` metadata and a `file.uploaded` audit event in Neon.
- At inspection, `v9.file_assets` contained 0 rows and `v9.audit_events` contained 0 `file.uploaded` events. The Cloudinary upload can therefore succeed while the application has no indexed, permission-scoped file record.
- The original logger recorded only the error class, not the SQLSTATE. The exact database error for those earlier uploads was not retained. The affected SQL also passed untyped parameters into the polymorphic `jsonb_build_object` audit constructor. The fix branch explicitly casts those audit values to `text`, logs the safe stage/error code, and prevents the UI from instructing the user to upload the same asset again when Cloudinary has already accepted it.
- Do not delete the Cloudinary objects. After the fix, reconcile any orphaned assets against the organization folder and file-owner metadata before cleanup or reattachment.

**Generator Dokumen Sekretariat**

- Vercel recorded `could not determine data type of parameter $41` on `/app/sekretariat/template/[code]`.
- Counting the bound parameters in `saveGeneratedSecretariatDocument` maps `$41` to the second `template.code` interpolation in the audit's `jsonb_build_object`. It is not linked to a typed SQL column at that use site, so PostgreSQL cannot infer its parameter type.
- The same JSONB object contains other dynamic values that need explicit type annotations. The fix branch casts `template.code`, `template.name`, `contentSha256`, `sourceReference`, and `resolvedSourceFieldKey` to `text`, and adds source-contract assertions for the failure pattern.
- The generator templates and action code exist, but the failed insert means the user's generated document/revision was not committed. No successful generation is inferred from the failed operation.

### 6.4 Governance and authority alignment

- V9 currently assigns only chair, organization administrator, and secretary roles (5 active assignments in total). No treasurer, member, government, NGO, or business-partner viewer role assignments were present.
- The 7 database organization units and 4 enabled field application records are technical registry data. The source field definitions still mark all four fields as `disiapkan` and leave definitive coordinators, appointment references, and periods as not recorded. These two status sources need reconciliation before the interface presents a technical switch as proof of an organization decision.
- The 5 old member records have not become V9 memberships. The one legacy profile that remains `pending_verification` with `not_requested` data consent must not be silently activated.
- The portal source explicitly states that no data-sharing grant registry exists. A viewer role alone is not a grant. External data must stay hidden until recipient, purpose, approved fields, expiry, and revocation are represented and tested.
- The notification screen is currently a shortcut/approval navigation surface, not a persisted inbox. The launcher explicitly says shared notifications are not active, and there is no V9 notification table in the current schema.
- `home.products` is saved as true while `features.productCatalogue` is false. The public home page checks both flags before showing products, so the product section is hidden and `/produk` remains intentionally disabled. This setting pair is inconsistent but is not the cause of the file-upload or generator failures.

### 6.5 Quality-gate limitations

The current CI runs source-contract scripts, TypeScript validation, and a Next.js production build. The repository contains no Playwright/Cypress/browser test files in the audited tree. Contract scripts can detect expected source patterns, but they cannot prove a real signed-in user's create/edit/save/reload/download/print/share sequence against Production Neon and Cloudinary.

The application also has 0/63 V9 tables with RLS enabled, and the `v9_app` role has broad CRUD grants. The current server-side `requireIdentity`, permission checks, and organization-scoped SQL are essential controls; the database itself does not yet provide row-level defense in depth.

### 6.6 Recommended completion order

1. **Persistence hotfix and verification:** merge/deploy the typed JSONB parameter changes; retry one upload and one document generation; verify the expected V9 rows and audit events. Reconcile rather than delete failed-upload Cloudinary assets.
2. **Authenticated module UAT:** verify account/profile, Website Studio, Secretariat CRUD/generator/print, finance journal workflow, field workplan workflow, file listing/download/share, and business/POS flows using appropriately assigned test users.
3. **Operational seed/import with approval:** map legacy member, program, secretariat, and public profile data into explicit target tables; preserve source IDs and consent/verification states; dry-run and reconcile counts before writes.
4. **Governance Studio completion:** add audited, permission-gated editors for organizational units/appointments, role assignments, module instances/toggles, theme presets/versioning, dashboard layouts, generic forms, and workflow definitions. Keep legal decisions separate from merely enabling a technical feature.
5. **Member, notification, and external-sharing foundations:** implement member lifecycle and scoped member access, a real notification/inbox/outbox model, and explicit data-sharing grants before promising these surfaces as operational.
6. **Security hardening:** design transaction-safe request context and staged RLS policies, test cross-organization denial in Preview, then deploy table-by-table. Do not enable RLS globally or revoke broad privileges as an untested bulk change.
