# V9.2 Global Post-Login Validation and Remediation

**Validation date:** 28 November 2026  
**Scope:** Production V9.2 integration branch, Neon production database, Vercel project environment, Cloudinary account usage, and server-side authorization implementation.  
**Safety boundary:** This review is read-only for production data. No production SQL writes, RLS changes, user-role changes, legacy imports, or secret values were applied.

## Executive status

- Production deployment is reported READY and the operator has confirmed successful login in the production browser.
- The recent production build and quality gate were reported successful in the prior release verification.
- Public pages previously checked returned HTTP 200. The `/produk` route returns 404 when the `productCatalogue` feature is disabled; that is the configured feature gate, not a server failure.
- A successful login does not yet constitute end-to-end acceptance of every authenticated module.

## Confirmed operational findings

### 1. File storage is not ready for application uploads

The Vercel project environment inventory contains no `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, or `CLOUDINARY_API_SECRET` entries. The upload implementation requires all three. As currently configured, the upload API responds with a controlled 502 response indicating that storage has not been configured.

The connected Cloudinary account reports a Free plan with 65 resources and approximately 180.1 MB of storage in use (usage snapshot dated 28 November 2026). This confirms an account with existing assets; it does **not** prove that the Srikandi Vercel runtime has the credentials required to upload or deliver them.

**Change in this branch:** an authenticated GET preflight on `/api/files` checks configuration readiness without returning credentials. The upload component now performs this check before sending file bytes, so users receive a clear readiness message rather than an avoidable failed upload. This does not replace the missing Vercel secrets.

**Required administrator action before upload UAT:** add the three Cloudinary values to Vercel Production and Preview environment targets through the secure Vercel interface. Do not paste the API secret into chat, code, GitHub issues, or repository files. After configuration, verify a real small test upload and download using an authenticated account, then remove the test asset if it is not a genuine organizational file.

### 2. Database access hardening

The production `v9` schema contains 63 application tables. At validation time, row-level security is enabled on 0 of 63. The `v9_app` role has application CRUD grants across this schema. Current isolation and authorization therefore depend on server-side identity resolution, permission checks, and organization-scoped SQL.

Do not enable RLS with a blanket migration. The application uses the Neon serverless HTTP query client, and its current shared query helper does not establish a per-request organization context or transaction-local security context. Enabling policies before refactoring that request context would cause legitimate reads/writes to fail or, worse, create policies that do not enforce the intended tenant boundary.

**Required implementation sequence:**
1. Inventory all reads/writes and their organization, unit, self, and public scope.
2. Add a request-bound database context mechanism that is transaction-safe with Neon HTTP pooling and cannot leak between requests.
3. Define policy tests for each role and scope, including anonymous/public access and cross-organization negative cases.
4. Enable RLS in a staged migration on a Preview database, run regression/UAT, then deploy only after measured verification.
5. Reassess broad DELETE grants separately; do not revoke them until the action inventory identifies every dependency.

No RLS or privilege changes were made in this branch.

### 3. Legacy data remains present and unmigrated

The legacy schema was inspected without reading or exporting personal field values. Counts observed:

| Source | Data found |
|---|---|
| `public.records` | 5 `anggota`, 1 `kelembagaan`, 1 `program`, 1 `register`, 1 `surat_resmi` |
| `public.settings` | 3 keys: two profile-specific settings and one public setting |
| `workspace_v14.member_profiles` | 1 pending-verification profile; consent status not requested |
| `workspace_v14.organization_memberships` | 2 active links: one admin and one chair |

These records have not been imported into V9 by this review. They were not deleted or altered. The V9 operational tables remain empty for several domains, including memberships, programs/activities, agriculture, training, finance, secretariat content, and file assets. The five user accounts and five role assignments that were previously verified in V9 are separate from the legacy profile/membership records.

**Required next step:** create a deterministic, idempotent mapping for each legacy record kind; verify source-to-target counts and duplicate handling; preserve source IDs and consent evidence; and produce a dry-run reconciliation report before any import. Do not import generic JSON records directly into operational tables without validating each payload schema.

### 4. Roles and external access

The active V9 role assignments observed were limited to chair, organization administrator, and secretary. No treasurer, member, government, NGO, or business-partner viewer assignments were present at the time of the audit. Do not interpret the existence of portal routes as proof that external users are provisioned or that data-sharing grants have been configured.

Before giving an external organization access, implement and test explicit recipient/data-sharing grants in addition to role assignment. The portal must expose only approved datasets and fields.

### 5. Login/runtime signal

A grouped set of 11 prior login-service errors for two users was present in Vercel runtime error reporting, with the most recent timestamp at 28 November 2026 09:20:41 WIB and the group associated with an earlier deployment. The operator subsequently confirmed that login works. The existence of this historical error group should be monitored; it is not evidence by itself that the current login flow is failing.

## Authenticated UAT still required

The deployment connector cannot reuse the operator's browser session. The following workflows therefore require browser validation by an authorized operator after the storage configuration is completed:

- Open the account/profile settings, save a profile change, refresh, and confirm persistence.
- Open Website Studio, save public-site settings, refresh the public page, and confirm the rendered result.
- Create, edit, and remove a non-critical test record in each active CRUD module; confirm database persistence after refresh.
- Test a small authorized file upload, file listing, download, and share-link permission boundary.
- Verify finance permissions using a treasurer account when one is formally provisioned; do not assign a real person to that role merely for testing.
- Verify member and external portal views only after appropriate test accounts and data-sharing grants exist.

## Release decision

This branch contains a low-risk storage-readiness improvement and this validation record. It does not change production data or enable RLS. Merge/release remains gated by passing CI, secure entry of Cloudinary credentials by the account owner, and authenticated UAT. RLS rollout and legacy import are separate controlled workstreams and must not be bundled into a quick production hotfix.
