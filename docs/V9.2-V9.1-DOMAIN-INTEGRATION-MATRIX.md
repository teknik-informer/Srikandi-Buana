# V9.2.0 to V9.1 Operational Data Integration Matrix

This document is based on direct inspection of the uploaded `Srikandi-Buana-V9.2.0-transfer.zip` source at `dist-package/sumber-lengkap/` and the current `feat/v9-operational-core` repository source. It is an implementation inventory, not a claim that integration is complete.

## 1. V9.2 demo boundaries confirmed in source

| Source | Observed behavior | Production treatment |
|---|---|---|
| `src/lib/store.tsx` | React context rehydrates and writes the full application state to browser localStorage (`sb_state_v7`). | Remove as authoritative operational persistence. Keep only ephemeral UI state where appropriate. |
| `src/lib/identity.ts` | Declares demo accounts and `sb_demo_session`; demo identities and passwords are hardcoded. | Do not port demo identities/passwords/cookie. |
| `src/lib/session.ts` | Resolves a browser cookie to a hardcoded demo identity. | Replace with V9.1 database-backed `getIdentity()`. |
| `src/app/actions/auth.ts` | Compares submitted password with hardcoded demo password and writes demo cookie. | Replace login action with V9.1 server authentication. |
| `src/app/actions/forms.ts` | Join-interest action validates fields but returns a generated reference without persisting the application. | Replace with persisted V9.1 membership-interest service. |
| `src/lib/site-settings.ts` | Studio settings saved/read from localStorage. | Replace with server-persisted CMS settings and publication permissions. |
| `src/data/*.ts` | Includes static demo collections for finance, members, programs, activities, products, orders, partners, documents, etc. | Use only as visual/reference fixtures in tests; never seed live production from these records. |
| `src/lib/finance.ts` | Calculates financial statements from in-memory/static journal collections. | Route all accounting reads/writes through native V9.1 finance services and database. |

## 2. Domain mapping

| V9.2 domain / screens | V9.1 operational source | Integration requirement |
|---|---|---|
| Public join form / membership interest | `v9.membership_interests`, `v9.people`, `v9.memberships`; `src/app/actions/membership.ts` | Persist submission, organization scope, consent metadata, review status and audit. Approval must not silently create an active account. |
| Member directory / member profile | `v9.people`, `v9.memberships`, `v9.user_accounts`, role assignments | Separate person, membership, account and role. Member status is not equivalent to login access. |
| Executive approvals | V9.1 authorization + audit events and domain-specific approval actions | Every approval checks organization scope, effective role, valid transition and records actor/time. |
| Secretariat letters / documents / expedition | V9.1 Secretariat migrations and document file API | Persist registers and metadata; files use protected server routes, not browser-only state. |
| Meetings / minutes / attendance / agenda | V9.1 Secretariat operational schema | Persist meeting, minutes and attendance; prevent duplicate attendance records. |
| Four field applications | `v9.field_applications`, `v9.organization_units`, assignments and field-domain tables | Enforce the four canonical field keys; field access is assignment- and scope-based, not inferred from menu visibility. |
| Agriculture / plots / cycles / visits / harvest | `v9.agriculture_plots`, `v9.agriculture_cycles`, `v9.agriculture_visits`, `v9.agriculture_harvests` | Persist plot/season/visit/harvest relationships; validate units and dates; preserve history. |
| Empowerment / training | V9.1 training and empowerment operations | Persist programs, sessions, participants, attendance and outcomes; do not show seeded demo metrics as live. |
| Business / partners / catalog / stock / orders | V9.1 partnerships, catalog, inventory and sales-order schema | Persist partner pipeline, product catalogue, stock movements and order lifecycle; stock changes must be transactional and auditable. |
| POS | V9.1 order and native-finance services | Sale completion must be atomic across order, inventory and accounting; no local-only checkout. |
| Native accounting | `v9.finance_journals`, journal lines, COA, cash/bank and integrity guards | Keep double-entry balance, approval, posting, immutability, maker controls and reversal rules in server/database layer. |
| Member / Government / NGO / Partner portals | V9.1 identity, role assignments, organization scope and explicit portal data services | Use least privilege and data minimization; do not expose internal records through client filtering alone. |
| Website Studio / public content | CMS boundary, separate from operational schema | Store content server-side with draft/review/publish workflow; do not use localStorage as the canonical published site. |

## 3. Canonical field applications

1. `organisasi` — Koordinator Organisasi & Keanggotaan.
2. `pertanian` — Koordinator Pertanian & Produksi.
3. `pelatihan` — Koordinator Pemberdayaan & Pelatihan.
4. `usaha` — Koordinator Usaha & Kemitraan.

The V9.2 UI route keys and V9.1 database field keys must be reconciled through an explicit mapping table and validated at the server boundary. A client-supplied field key is not proof of authorization.

## 4. Integration order

### Phase A — identity and public entry
- Replace demo session and login with V9.1 session contract.
- Replace join form demo response with V9.1 persisted membership interest.
- Add error/empty/loading states for unconfigured database and unauthenticated states.
- Preserve V9.2 login layout and branding while replacing only its authentication behavior.

### Phase B — Secretariat and membership
- Member register and status management.
- Incoming/outgoing letters, documents, file access and expedition.
- Meetings, minutes, agenda and attendance.
- Add integration tests for organization scoping, duplicates and audit events.

### Phase C — four field applications
- Field dashboard summaries from database queries.
- Staff, assignments, work plans, tasks, activities and calendars.
- Agriculture, training and business domain records.
- Confirm all field-specific route segments resolve to canonical database field keys.

### Phase D — finance, inventory, commerce and POS
- Bind every financial screen to V9.1 server-side finance queries/actions.
- Bind stock and orders to transactional inventory/order services.
- Verify POS sale atomicity and corresponding accounting entry.
- Keep finance reversal and posting protections unchanged.

### Phase E — portals, Studio and public CMS
- Role-scoped portal read models.
- CMS content persistence, preview, review and publish permissions.
- No operational-data authoring through CMS.

### Phase F — release qualification
- Typecheck, production build, unit/integration/e2e.
- Test roles and forbidden access at server boundaries.
- Responsive checks at 320, 360, 375, 390, 414, 430, 600, 768, 820, 1024, 1280, 1366, 1440 and 1920 px.
- Preview-only deployment; user acceptance before production promotion.

## 6. Safety constraints

- No production environment variable changes while the target project/branch mapping is unverified.
- No destructive SQL, database reset, or replacement of the V9.1 development database.
- No demo account, sample financial transaction, or sample member record copied into live organization data.
- No Production deployment, domain reassignment, or promotion before user acceptance.
